# Event site: what we changed on the `user_website` branch, and why

A walkthrough of everything done to PR #59 ("Add user website") after checking it
out, written for the people who wrote it. The point is not the list of changes —
it is the reasoning behind each one, and the handful of mistakes worth not
repeating. Several sections say "we were wrong"; those are the useful ones.

**Date:** 13 August 2026
**Branch:** `user_website`
**Net effect:** 75 files changed, ~5,900 added, ~7,700 removed

---

## 1. What the PR contained

51 new files, +13,876 lines, all under a new top-level `user_website/` — a second,
independent Vite/React app with its own `package.json`, lockfile, and `tsconfig`.
Zero changes to `server/` or `client/`. It covered the participant side: auth,
profile, event browsing, team registration, accommodation, UPI payment, feedback,
certificates.

As a UI prototype it was a solid piece of work. The problems were about how it
connected — or didn't — to everything else.

---

## 2. Triage: what we found first

### The build was broken

`npm run build` runs `tsc && vite build`. It failed:

```
RegistrationPage.tsx(208,7): error TS2353:
  'dataUrl' does not exist in type 'RegistrationDocument'
```

**The important part is not the error, it's that CI passed anyway.** The workflow
in `.github/workflows/pull-request.yml` installed only `client` and `server`; root
`typecheck` and `build` were both `--prefix client`. The new app was invisible to
every automated check.

> **Lesson.** Adding a new app means wiring it into CI in the same commit.
> A green tick that isn't checking your code is worse than no tick, because
> everyone believes it.

ESLint had the same gap: the TypeScript/React/import-order rules were scoped to
`client/**/*.{ts,tsx}`, so the new files fell through to bare
`js.configs.recommended` — no TS rules, no hooks rules. And because `lint-staged`
runs `eslint --fix` on staged `.tsx` files, it _looked_ linted while getting almost
none of the real rules.

### 2.3 MB of committed junk

`new.txt` (1.16 MB) and `old.txt` (1.13 MB) were UTF-16 directory listings.
`event_reg_backup.txt` was a 28 KB single-line backup.

> **Lesson.** Before committing, run `git status` and look at every file. Scratch
> files and backups belong outside the repo, or in `.gitignore`. Git keeps them
> forever once committed, even after deletion.

### `package.json` was copy-pasted

31 dependencies were declared. We grepped every import in the app; **six** were
actually used: `clsx`, `lucide-react`, `react`, `react-dom`, `react-router-dom`,
`tailwind-merge`.

The rest came from the staff client: MSAL, CASL, FullCalendar, jspdf, pdf-lib,
socket.io-client, bootstrap, react-select, axios, dotenv, uuid, jwt-decode — and
**`mysql2`, a MySQL driver, in a browser bundle**. Install dropped from 270
packages to 86.

> **Lesson.** Start a new app's `package.json` empty and add as you import.
> Copying another project's dependency list ships code you never audited.

### The app could not show a single event

The whole app made exactly one network call — `GET /api/events/public` — and
**that endpoint did not exist**. Worse, the shape it expected didn't either: it
read `title, category, startDate, venue, fees, participation, teamSize,
hasAccommodation`, but the `events` table had four columns (`id, title, status,
timestamps`). Category, fees, participation and accommodation existed nowhere in
the schema, and there were no tables for registrations, payments or feedback.

So the frontend was written against an imagined API. That is a reasonable way to
prototype, but it has to be stated, because the backend was the bulk of the real
work and none of it was in the PR.

## 3. Things that looked fine and were not

### Authentication was fake

```js
const login = useCallback(async (email, _password) => {
  await new Promise((r) => setTimeout(r, 600));
  const u = { email, name: email.split('@')[0] };
  setUser(u);
  localStorage.setItem('ep_auth', JSON.stringify(u));
}, []);
```

Any email and any password produced a logged-in user. No token, no server call.
Every "protected" route was decorative — and the signup and password-reset forms
(283 lines) faked success too.

> **Lesson.** UI that pretends to work is more expensive than a missing screen. A
> reviewer sees a working login and assumes auth is done.

### Payment was self-service

The participant clicked a button and the client set `paymentStatus: 'paid'` **and**
`reviewStatus: 'selected'` on itself. The UPI ID was the placeholder
`'eventpro@upi'`, and the QR was generated by third-party `api.qrserver.com` with
the amount in the URL.

> **Lesson — the one rule to remember.** Anything involving money, eligibility, or
> approval is decided by the server. The browser is an untrusted input device. It
> may _ask_; it may never _decide_.

### A debug panel that shipped to the public

The header had a "Server Connectivity" popover letting anyone type a backend
address, persisted to `localStorage`, with the text:

> _"If your friend's IP address changes, enter the new IPv4 or localhost address
> below to reconnect."_ — placeholder `10.40.242.123:5000`

On a public site that lets a visitor repoint the app at an attacker's backend, and
it leaks internal IP conventions. Removed; the online/offline badge stays, and the
API host now comes from build-time env config.

### Data leaking between users

Registrations and profile were keyed per email, but `ep_feedbacks`,
`accommodation_payment_proof`, `ep_personal_status` and `ep_professional_status`
were **global** keys. On a shared browser the next user saw the previous one's data.

> **Fixed.** `shared/storage.ts` now owns every key: `readScoped`/`writeScoped`
> namespace by participant email, `STORES` names each store in one place so a
> reader and a writer cannot drift, and `clearAppStorage()` runs on logout so
> nothing survives the session on a shared machine.

### Files as base64 in localStorage

Payment screenshots and ID cards were read with `FileReader.readAsDataURL` and
persisted. Two phone screenshots exceed the ~5 MB quota, and the `try/catch`
swallowed the failure — so data vanished with no error.

> **Lesson.** `localStorage` is a ~5 MB string cache, not a database, and never a
> file store. Files go to the server via Multer; the DB stores the path.

### Hardcoded demo logic in a real code path

```js
export function isAiHackathon(event) {
  return event.eventName === 'AI Hackathon 2026';
}
if (event.eventName === 'Build Battle') return 'Selected';
if (event.eventName === 'Idea Pitch') return 'Rejected';
```

These fed `isPayableEvent`, so **who was allowed to pay depended on string-matching
event names**. Accommodation room types and prices were hardcoded too.

> **Lesson.** Demo data belongs in a seed script, never in a branch condition. If
> you must stub, name it (`FALLBACK_`, `LEGACY_` — see CLAUDE.md) so it is
> greppable and deletable.

> **Fixed.** Both helpers are gone. `getReviewStateLabel(registration)` derives
> the badge from `reviewStatus` alone, and `isPayableEvent` keys off the same
> field. Until the backend fills `event_registrations.review_status` every
> registration reads as `'pending'`, so no event shows a decision it has not been
> given — where the name-matching used to invent one. `markPaymentDone` no longer
> writes `reviewStatus: 'selected'` either: paying is not being shortlisted.

## 4. Restructuring — including the part we got wrong

`user_website/` was renamed to **`event-client/`** (a sibling of `client/` and
`server/`), the pointless nested `client/` level removed, and files grouped by
feature.

First attempt mirrored the staff client exactly: `features/<domain>/components/`
plus `features/<domain>/styles/`. Then we counted:

| Feature                                                       | Components | Stylesheets |
| ------------------------------------------------------------- | ---------- | ----------- |
| auth, home, profile, feedback, certificates, my-registrations | 1 each     | 1 each      |
| payment, registration                                         | 2          | 2           |
| events                                                        | 3          | 3           |

**Six of nine features held a single file in each directory.** A folder wrapping one
file buys nothing, and it pushed every stylesheet three levels from its component.
Flattened to one directory per feature, with the CSS beside the component
(`import './HomePage.css'`). Directory count went 30 → 16.

> **Lesson.** Copying a convention because it exists elsewhere is not consistency,
> it is cargo-culting. The staff client earns `components/` + `styles/` because its
> features hold dozens of files. Add structure when the file count demands it, not
> in advance. The valuable boundary was `features/<domain>/` — that stayed.

A side effect worth knowing: all 16 CSS files start with
`@reference "../index.css"` for Tailwind v4, and moving them broke every one. The
build failed loudly, which is how we found it — a good argument for running the
build after any move.

### Dead code found while getting lint to zero

Twelve unused declarations, plus two real finds:

- **`handleIdChange` was defined twice** in `ProfilePage.tsx` — an identical inner
  copy shadowing the memoised `useCallback`, so the memoisation did nothing. Kept
  the outer, deleted the duplicate.
- `FeedbackPage.tsx` had a `useMemo` depending on `success`, which ESLint flagged as
  unnecessary. It is **not** unnecessary: it is a deliberate cache-buster, because
  `localStorage` is not reactive. "Fixing" the warning would have broken the
  refresh-after-submit. We added `void success;` with a comment instead.

> **Lesson.** A linter reports patterns, not intent. When a warning looks wrong,
> work out why the code is that way before changing it — and if the code is right,
> record why so the next person doesn't silently "fix" it.

## 5. The schema decision, and how counting changed the answer

The admin-side schema (`events_final.sql`, now
`server/schema/migrations/20260812_events_module.sql`) modelled a participant as:

```sql
`user_id` int NOT NULL,
CONSTRAINT `fk_reg_user` FOREIGN KEY (`user_id`) REFERENCES `users` (`id`),
```

That is a problem. The event site authenticates the general public via Gmail, so
every signup would land in `users` — where `findOrCreateUser` inserts them and
`ensureUserHasBaseRole` grants the base `user` role. A plain authenticated identity
is enough to reach every route guarded by `authMiddleware` alone (events, journals,
projects, master-data, user-dashboard: only 8 of ~22 route files use
`permissionMiddleware`). Random Gmail accounts would get read access to internal
data.

**Our first recommendation was wrong.** We said keep the FK and add a
`user_type` discriminator, on the grounds that "30 FKs already point at `users`, so
repointing is a rewrite." Then we actually counted:

| FK column → `users`                        | Count | What it is             |
| ------------------------------------------ | ----- | ---------------------- |
| `created_by` / `updated_by` / `deleted_by` | 82    | staff audit — stays    |
| `verified_by`                              | 1     | staff verifier — stays |
| `user_id`                                  | **1** | the participant        |

Eighty-two were staff audit columns that legitimately point at `users`.
`event_certificates` and `event_feedbacks` reach the participant through
`registration_id`, not `user_id`. Moving public identity into its own table was a
**one-FK change**.

That flipped the decision. The discriminator approach would have made safety depend
on every future developer remembering `AND user_type = 'staff'` in the right
queries — a permanent obligation that grows with the codebase. A separate
`event_participants` table makes the separation structural: public rows simply
cannot enter the table that drives RBAC.

> **Lesson 1.** Check the number before you reason from it. A wrong estimate led to
> a worse architecture, and one `grep | sort | uniq -c` corrected it.
>
> **Lesson 2 — secure by construction beats secure by vigilance.** Prefer designs
> where the mistake is impossible over designs where it is merely forbidden.

### Other schema gaps found

- **No team members table.** `event_registration_settings` had `team_enabled` and
  min/max sizes, and `event_registration_fees` had `team_fee` / `member_fee` — but
  nowhere stored the members. Added `event_registration_team_members`.
- **No payment proof column.** `event_payments` already had `verified_by` /
  `verified_at` (correct!), but nothing to hold the screenshot the verifier looks
  at. Added `proof_file_path`.
- **Accommodation could not price itself.** One flat `fee_amount` per event cannot
  express "AC room costs more than a dormitory". Added a per-event room-type
  tariff table and per-registration room rows.

Two design details in that last one are worth copying:

- **Snapshot prices.** `price_per_night_snapshot` is stored on the booking, so an
  admin editing the tariff later cannot silently rewrite what past participants
  were charged.
- **Derive, don't duplicate.** `nights` is a generated column computed from the
  check-in/check-out dates, so it can never disagree with them.

## 6. Testing the migration instead of reviewing it

We ran both migrations against a scratch MySQL database. Three real defects
surfaced that reading had missed:

1. **`events_final.sql` did not run at all.**
   `ERROR 1824 at line 304: Failed to open the referenced table 'resource_persons'`
   — that table ships in a different module and does not exist in production. Worse,
   our own conditional-FK fix was **dead code**, because the FKs were declared
   _inline_ in `CREATE TABLE`, so the script died before any later migration ran.
   Fixed by removing the two inline constraints and attaching them conditionally.

2. **A CHECK constraint we wrote was illegal.** MySQL rejects a CHECK on any column
   with a foreign-key referential action (errno 3823), and `fk_pay_verified_by` is
   `ON DELETE SET NULL`. So "Verified requires `verified_by` and `verified_at`"
   cannot be a database constraint — it has to live in the verification handler,
   and that is now documented where someone will read it.

3. **Our safety guard printed a useless error.** It correctly refused to run when
   `event_registrations` already held rows (data intact), but `MESSAGE_TEXT` is
   capped at 128 characters, so the helpful message became
   `Data too long for condition item`.

> **Lesson.** A migration you have not executed is a guess. Spin up a scratch
> database, run it, run it **twice** to prove idempotency, and try the failure path
> on purpose. All three of these were invisible to careful reading.

## 7. What was built

### Backend

| File                                        | Purpose                                                               |
| ------------------------------------------- | --------------------------------------------------------------------- |
| `config/participantAuth.js`                 | Token contract: separate secret (required in production), `aud` claim |
| `middleware/participantAuthMiddleware.js`   | Sets `req.participant`, never `req.user`                              |
| `middleware/authMiddleware.js`              | Now **rejects** participant tokens                                    |
| `middleware/participantUploadMiddleware.js` | Multer per category, mime allow-lists, size caps                      |
| `modules/participantAuth/`                  | Google login (any Gmail) + session restore                            |
| `modules/events/public/`                    | The unauthenticated projection the event site reads                   |
| `modules/participantRegistration/`          | Participant writes — scaffolded, see its README                       |

The boundary is enforced twice on purpose: a separate signing secret **and** an
`aud` claim checked by both middlewares. The tests deliberately set both secrets to
the same value, proving the `aud` check alone still holds if they are ever
misconfigured to match.

### Route mount order — a subtle trap

`GET /api/events/public` returned "Authentication required" despite being public.
Cause: `app.use('/api', journalRoutes)` sits earlier in `server.js` and calls
`router.use(authMiddleware)`, so it intercepts **every** `/api/*` request. Public
routes must be mounted above it.

> **Lesson.** Express middleware order is program logic. A router mounted at a
> broad prefix affects everything registered after it.

### Frontend

`AuthContext` now performs real Google OAuth and, importantly, **revalidates the
stored token on load** rather than trusting it — so a blocked account cannot keep a
stale session. `ProtectedRoute` waits for that check, otherwise a refresh bounced
signed-in users to `/login`.

`config/api.ts` centralises the API base, token storage, and an `apiFetch` that
unwraps `{ success, data }` and clears the token on `shouldLogout`.

## 8. Small things that cause big confusion

- **`strictPort: true`** on the event site's Vite config. Vite silently moved to
  3002 when 3001 was busy — and since only `http://localhost:3001` is whitelisted
  as a Google OAuth origin, that surfaces as a baffling "origin not allowed" error.
  Now it fails loudly with the real reason.
- **`npm run dev` starts all three** apps with named prefixes
  (`[server] [client] [event]`), plus `dev:staff` and `dev:public` for pairs.
- **Prettier reformatted two unrelated files** when we ran it across `server/`.
  Reverted. Keep a diff to the work it claims to contain — unrelated churn hides
  real changes during review.

## 9. The rules, condensed

1. The server decides anything involving money, eligibility, or approval.
2. Never trust a client-supplied amount. Recompute from the source table.
3. Check ownership before acting on `:id`. Return 404, not 403, so a probe cannot
   confirm the record exists.
4. Files go through Multer to `server/uploads/`; the DB stores the path.
5. `localStorage` is a cache, not a database, and never a file store.
6. Wire new code into CI, ESLint and Prettier in the same commit.
7. Run migrations against a scratch DB — twice — before proposing them.
8. Count before you reason from a number.
9. Prefer designs where the mistake is impossible over designs where it is banned.
10. Demo data goes in a seed script, never in an `if`.

## 10. What is still open

- `modules/participantRegistration/` is a scaffold. The security-critical parts
  (ownership, eligibility, accommodation pricing, payment-proof insert) are done
  and tested; the CRUD is marked `TODO(intern)`. **Read that module's README
  first** — it lists the four rules that must not be broken.
- `submitPaymentProof` answers **501** until the amount is computed server-side.
  It previously inserted `amount = 0`; a payment row carrying a number nobody
  computed is worse than no row, because staff verify against it and it
  reconciles to zero without ever looking wrong. The amount is the one number
  that must be right, so the route refuses rather than guessing.
- Registrations, payments and feedback still persist to `localStorage` on the
  frontend until those endpoints exist. Every key is now namespaced per
  participant via `shared/storage.ts` and wiped on logout, so a shared browser no
  longer leaks one participant's data to the next — but this is a cache standing
  in for a database, and it goes away when the endpoints land.
- Accommodation room types are served per event by the API now; the frontend still
  uses its hardcoded list.
- The UPI payee (`eventpro@upi` / `EventPro` in `PaymentPage.tsx`) is still a
  placeholder and must come from the event before this takes real money.
- `express-rate-limit` is already a dependency but commented out. The public
  endpoints are unauthenticated — enable it before this faces the internet, and
  put a per-participant limit on the four upload routes first: they accept 2-5 MB
  from any signed-in account, and Multer writes to disk before ownership is
  checked, so one account can fill the volume.
- `server/modules/events/` still implements the _legacy_ design and queries tables
  (`pre_events`, `coordinators`, `budgets`) that no longer have a schema. It is
  superseded and should be retired in its own PR.
- The coordinator block in `RegistrationsPage.tsx` is **removed, not hidden**. It
  showed one hardcoded staff member's name, mobile and email on every event.
  Restore it once `/api/events/public` carries per-event coordinator fields the
  event owner has approved.

### Three the bots raised that were left for you on purpose

These are real, and each was deferred because the durable fix is a participant
endpoint, not a client-side patch. Do not paper over them in `event-client/`.

1. **The session outlives the browser.** The token lives in `localStorage`, so on
   a shared machine the next person opens the site already signed in as the
   previous participant. Per-key scoping does not help — the token itself is the
   leak. `sessionStorage` closes it but drops the session on every tab close,
   mid-registration, so it is a product decision. Raise it before launch.
2. **`EventItem.fees` is the _lowest_ applicable fee, and the registration and
   payment flows spend it as if it were the final price.** Fees vary by
   participant type, and the public list cannot know the type of someone who has
   not signed in. When you build the profile endpoints, return the exact fee for
   the participant's type and have the payment flow refuse to total an
   unresolved one — showing a range is fine, charging a range is not.
3. **"Clear All" on the payment summary calls `clearRegistration`,** which deletes
   the whole entry: team members, form status, uploaded document, payment proof.
   The control sits under "Selected Events", so it reads as a selection reset.
   Separate the payment selection from the registration record when
   `/registrations` exists.

## 11. Review fixes applied after this walkthrough was written

A review of the branch turned up eight defects. All are fixed; this section says
what changed and, where it matters, what you are expected to undo.

### Backend — keep these

**`getParticipantGoogleClientId()` throws instead of returning `undefined`** —
`config/participantAuth.js`. google-auth-library skips audience verification
entirely when `audience` is undefined, so an unset env var meant an ID token from
_any_ Google OAuth app would verify: sign-in as any email. The OAuth client is now
built on first login rather than at import, so a missing var cannot stop the
shared server — and with it the whole staff portal — from booting.

**Login matches soft-deleted rows too** — `participantAuthModel.js`.
`uq_participants_email` and `uq_participants_google_sub` are unconditional, so
filtering `is_deleted = 0` sent a returning removed participant into an `INSERT`
that died on `ER_DUP_ENTRY`: an unrecoverable 500 on every future sign-in. The row
comes back untouched and login refuses it with a reason, because reviving it would
silently undo an admin's decision.

**Login checks `is_deleted`, `is_blocked` and `is_active`** —
`participantAuthController.js`. The same three the middleware enforces. An
inactive account used to receive a working token and then fail every request with
a misleading "Participant account not found".

**Multer rejections return 400 `{ success, message }`** —
`participantUploadMiddleware.js`, wired at the end of
`participantRegistrationRoutes.js`. They used to fall through to the app-wide
handler's 500 `{ error }`, a shape `apiFetch` cannot read, so an oversized file
told the participant "Request failed (500)".

**Failed uploads delete the stored file** — `removeUploadedFile` / `failUpload`.
Multer writes to disk before the handler runs, so every 500 from an unimplemented
endpoint left an orphan behind.

**This one is on you:** every upload handler must fail through `failUpload`, not
`fail`. If you add a route that takes a file, the same rule applies.

### A second pass, from the bot reviews

CodeRabbit and Greptile raised 64 comments between them. Most were style; these
were real, and all are fixed:

- **Uploads accepted any file that claimed an allowed MIME type.** `file.mimetype`
  comes from the client and `sanitizeUploadFilename` keeps the extension, so
  `evil.html` sent as `image/png` landed on disk as `.html` — and
  `express.static` serves that as `text/html` from the API origin, which in
  production is the staff portal's origin. Each MIME type is now bound to its
  allowed extensions, `/uploads` sends `X-Content-Type-Options: nosniff`, and
  participant directories send `Content-Disposition: attachment` (subresource
  loads ignore it, so `<img>` still renders).
- **Accommodation was priced per occupant.** `price_per_night` sits beside
  `max_occupants` — the capacity of one room at that rate — so it is a per-room
  rate. Multiplying by occupants billed a 2-person room for 2 nights at 4x.
- **`min_fee` collapsed to NULL** whenever one fee column was 0, which is the
  normal shape for an event that prices only individuals or only teams. The site
  advertised paid events as free.
- **A self-referencing `parent_id` 500'd the whole public catalogue** —
  `JSON.stringify` throws on the cycle the nesting loop built.
- **Concurrent first sign-ins raced to a duplicate-key 500.** A double-clicked
  Google button was enough.
- **The certificate preview showed one hardcoded name to every participant**, and
  the registration modal showed one hardcoded coordinator's name, mobile and
  email on every event. Both were demo data on a live path; the same class of bug
  as the event-title matching in §3.
- **A paid registration still offered an enabled "Register Now"**, which routed
  back through the form to `/payment` for an event already paid for.
- **`SelectedAccommodation.pricePerNight` actually held a total.** Renamed to
  `amount`. The bots proposed multiplying it by `nights`, which would have
  double-charged — worth knowing that a plausible-looking suggested fix was
  wrong.
- Unbuilt endpoints answer **501**, not 500, so a real fault stays visible.
- The migration backfills use `NOT EXISTS` guards rather than `INSERT IGNORE`,
  which only suppresses duplicates on a UNIQUE key that these tables lack; and
  legacy status values are normalised before the CHECK constraints are added,
  since one stray `'Paid'` would abort the ALTER and leave the DB half-migrated.

New tests: `participantLoginGuards.test.js`, `participantUploadErrors.test.js`,
`participantAccommodationPricing.test.js`, `publicEventsNesting.test.js`.
Suite is 222 across 20 files, up from 193 across 16.

Three findings were deliberately **not** fixed — see the end of §10 for what they
are and why they are yours.

> **Lesson — a confident review comment can still be wrong.** Both bots said
> `PaymentPage` should multiply `pricePerNight` by `nights`. Doing that would
> have charged every stay twice: `Accommodation.tsx` was already writing the full
> computed total into a field _named_ `pricePerNight`. The fix was to rename the
> field to `amount`, which removes the trap instead of patching one call site.
> Both bots also filed the same "registrations are overwritten on refresh" bug
> against `EventsContext`, which the `key` in `App.tsx` prevents — and
> CodeRabbit's own comment on `ProfileContext` says so explicitly. Verify against
> the code before acting, including on a 🔴.

### Frontend — one of these is temporary

**`shared/storage.ts` is a stop-gap. Delete it when your endpoints land.**

`ep_feedbacks`, `accommodation_payment_proof`, `ep_personal_status` and
`ep_professional_status` were global keys — on a shared browser (lab, help desk,
registration counter) the next participant saw the previous one's data. Rather
than scatter more per-email key building around, all browser persistence went
behind one 45-line module:

- `readScoped` / `writeScoped` — namespace by participant email
- `STORES` — names each store once, so a writer and a reader cannot drift apart
- `clearAppStorage()` — called from `AuthContext.logout`, wipes every `ep_*` key

When `GET/PUT /api/participant/profile`, `/registrations` and `/feedback` exist,
the four call sites (`FeedbackPage`, `HomePage`, `ProfilePage`, `PaymentPage`)
swap `readScoped`/`writeScoped` for `apiFetch` and the file reduces to the auth
token in `config/api.ts`. It is deliberately small so that removal is mechanical.

The rest are permanent:

- **The payment QR is rendered in-browser** (`qrcode`) rather than fetched from
  `api.qrserver.com`. A QR standing between a participant and a payment must not
  depend on a third party being up, and the payee VPA and amount were not theirs
  to receive. Falls back to showing the UPI ID as text if rendering fails.
- **`isAiHackathon` and the `Build Battle` / `Idea Pitch` matching are gone** —
  see §3. `getReviewStateLabel(registration)` and `isPayableEvent` read
  `reviewStatus` alone. **This is the field you fill:** until
  `event_registrations.review_status` is served, every registration reads
  `'pending'` and no event shows a decision it was not given. Wire that column
  through and the shortlist UI lights up with no frontend change.
- **`markPaymentDone` no longer sets `reviewStatus: 'selected'`.** Paying is not
  being shortlisted; only staff make that call.
- **`apiFetch` also reads `body.error`**, so messages from Express's app-wide
  handler reach the user instead of "Request failed (500)".

# Appendix A — Full decision log

Every decision taken, the options considered, and the reason. Decisions marked
**[product]** were made by the team; the rest were engineering calls.

### A1. Keep the event site as a separate app, or fold it into `client/`?

**Chose:** separate app (`event-client/`), separate build, shared backend.

One reason outweighed the rest: **the public bundle must not contain staff code.**
If both apps shared one entry tree, admin screens, CASL ability definitions and the
internal API surface would all end up in JavaScript downloadable by anyone at
`event.ksrct.ac.in`. Code-splitting does not fix that — the chunks are still
fetchable. Separate builds make the leak structurally impossible, and it matches
the IIS plan of one site per subdomain.

Accepted cost: duplicated types and API client, plus version drift. Drift is the
one that bites, so versions are pinned to match `client/` (React 18.3, Vite 6,
TS 5.9).

### A2. How does public Gmail login coexist with staff login?

First we established what actually restricted logins today. **There is no domain
check anywhere in the code** — not in `authController.googleLogin`, not in
`findOrCreateUser`, and no `hosted_domain` on the staff `<GoogleLogin>`. The
`@ksrct.ac.in` restriction lives _only_ in the Google Cloud console (the OAuth
consent screen is Internal / Workspace-only).

That matters: flipping that same client to External to allow Gmail would have
opened the staff portal too.

**Chose:** two separate identity tracks.

| Concern      | Decision                                                                                               |
| ------------ | ------------------------------------------------------------------------------------------------------ |
| OAuth client | A second client ID with an External consent screen for the event site; staff client untouched          |
| Storage      | New `event_participants` table — never `users`                                                         |
| Token        | Separate `JWT_PARTICIPANT_SECRET` **and** `aud: 'participant'`                                         |
| Rejection    | Two-way: `authMiddleware` refuses participant tokens, `participantAuthMiddleware` refuses staff tokens |
| Namespace    | `/api/events/public` (open), `/api/participant-auth`, `/api/participant`                               |

Two mechanisms rather than one is deliberate. The separate secret is the primary
boundary; the `aud` check is what still holds if the secrets are ever unified or
misconfigured to the same value. The tests set both to the same value on purpose to
prove that.

**Also recommended (not yet done):** harden the staff login with
`hosted_domain="ksrct.ac.in"` on the button _and_ a server-side check of
`payload.hd` and `payload.email_verified`, since the console setting is currently
the only thing protecting it.

### A3. Password login as well as Gmail? **[product]**

**Chose:** Gmail-only. Signup and password-reset forms deleted.

Not because hashing is hard — because the project has **no email infrastructure**:
no `bcrypt`, no `nodemailer`, no SMTP config anywhere. A real password flow needs
verification tokens, reset tokens, rate limiting, and a working outbound mail path
with SPF/DKIM on the college domain. The mail piece is an infra and DNS
conversation, not a coding task. Google OAuth gives verified email addresses for
free, with no passwords to store.

Revisit only if real users cannot sign in with Google. Adding it later is no harder
than adding it now.

### A4. Are participants linked to staff `users` rows? **[product]**

**Chose:** no linking. A staff member registering for an event gets an
`event_participants` row that is entirely unrelated to their `users` row. Simpler,
and it keeps A2's separation absolute.

### A5. Where do participants appear for admins? **[product]**

**Chose:** a new admin screen inside the **staff portal**, organised **per event**.

Per-event rather than one flat list, because that is already the security boundary:
if a coordinator may only see their own event, then "event" is the natural
navigation unit, every query is `WHERE event_id = ?`, and it cannot leak another
department's data through a forgotten filter. A flat list looks convenient at 50
rows and collapses at 5,000. A cross-event view for super-admins can sit on the same
endpoint later; retrofitting scoping onto a flat list is the migration you do not
want.

Participants do **not** appear in the existing access-control screens — that is the
staff RBAC screen, and participants have no roles.

### A6. Which permission scopes the admin view? **[product]**

**Chose:** the keys already seeded by the events migration — `event.view`,
`event.register`, `event.manage_registration`, `event.generate_certificate`,
`event.manage_feedback` — and **dropped the `event_registration.view` key we had
invented**.

Per-coordinator scoping needs no new table: `event_coordinators (event_id,
employee_id)` already exists, so the rule is

> `event.manage_registration` **and** a row in `event_coordinators` for that event
> (super-admin bypasses).

We added three keys the seed lacked: `event.verify_payment`,
`event.manage_accommodation`, `event.manage_participants`. Payment verification is
split out deliberately — signing off money is a stronger grant than editing a
registration list, and the two should be assignable separately.

### A7. Accommodation: shrink the frontend or extend the schema?

**Chose:** extend the schema.

The schema had one flat `fee_amount` per event; the UI already offered room types at
different nightly rates, occupancy, multiple rooms and travel dates. A single fee
cannot express "AC room costs more than a dormitory", which is an ordinary
requirement — so the limitation was in the schema, not the UI. Added
`event_accommodation_room_types` (per-event tariffs) and
`event_registration_accommodation_rooms` (per-booking rows), plus stay dates.

There was no existing guest-house schema to reuse — `GuestHouseBooking.tsx` is
frontend-only with no backend tables — so pricing lives in the events module.
`room_allocation_id` remains the hook for a future allocation module.

### A8. How is a fee shown when fees vary by participant type?

**Chose:** the public list returns a **range** (`feeRange: {min, max}`); the exact
fee is resolved once the participant's type is known.

`event_registration_fees` is per `participant_type_id` with four amounts. A visitor
browsing events has no participant type yet, so no single number is correct.
`participant_type_id` was promoted onto the participant profile so fee resolution is
a real join.

### A9. Participants in `users`, or their own table?

Covered in §5 — this is the decision we **got wrong first and reversed after
counting**. Final: own table, `event_participants`.

### A10. How is the ~35-field profession profile stored?

**Chose:** normalised core columns + `profession_details` JSON.

The fields are profession-type-conditional (a school student has
`classGrade`/`parentGuardian`; faculty has `designation`/`qualification`; industry
has `organization`) across 11 profession types. Options were a wide table of ~50
mostly-NULL columns (every new profession type = `ALTER TABLE`), EAV (painful to
query), or core + JSON.

Core + JSON follows a pattern **already established in this schema** by
`events.workflow_state` with generated columns. The seven fields an admin list
filters on (`participant_type_id`, `profession_type`, `institution`, `department`,
`designation`, `register_number`, `id_card_path`) are real indexed columns;
everything else is JSON. Age is **derived, never stored**.

### A11. Amend the events migration in place, or layer a delta?

**Chose:** a separate delta migration (`20260813_...`), except for two surgical
fixes to the events file itself.

The events module is not deployed (production has zero events tables), so amending
in place was tempting. But developer machines may already have run it, so the delta
is written to be **idempotent and self-healing** — it repairs an older run rather
than assuming a clean slate. The two exceptions were the inline `resource_persons`
FKs, which had to be removed from the original file because they aborted the script
before any delta could run.

### A12. What to do about `resource_persons` not existing?

**Chose:** attach both FKs conditionally, via a helper that only adds the
constraint when the referenced table exists.

Rejected: duplicating that table's DDL, because the legacy definition is the **wrong
shape** — it is event-scoped (`event_id NOT NULL`, cascade delete), whereas
`event_resource_persons (event_id, resource_person_id)` with a uniqueness pair only
makes sense if `resource_persons` is a standalone master reusable across events.
Copying it would have baked in a contradiction. The migration now runs standalone
and picks up the constraints when that module lands.

### A13. Retire `legacy/04_events.sql`, or guard it? **[product input]**

**Chose:** delete it.

It opened with `DROP TABLE IF EXISTS events, pre_events, resource_persons, …` and
rebuilt the old 4-column `events`, so running it after the migrations destroyed the
module. Four checks before removing: nothing executes it (no script, no CI step);
the tables held no data and were unreleased; its design is superseded; and its
`resource_persons` is the wrong shape anyway (see A12). A guard would have preserved
a footgun whose only value was documenting a design being replaced. Git history
keeps it, and the recovery path is noted in `server/schema/README.md`.

### A14. What makes an admin-posted event publicly visible?

**Chose:** `workflow_status = 'completed' AND is_active AND NOT is_deleted`.

Determined by reading `workflowService.js`, which writes **lowercase** statuses:
`in_progress` → `completed` / `rejected` / `archived`. `'Draft'` turned out not to be
a mismatch but the pre-submission default of the generated column — so we normalised
its casing to `'draft'` for consistency. Verified by seeding one approved, one draft
and one in-review event and confirming only the approved one is returned.

Registration is separately open when `registration_status IN ('Ongoing','Extended')`,
the deadline has not passed, and capacity is not reached.

### A15. Folder structure: mirror `client/`, or flatten? **[product]**

**Chose:** flatten. See §4 — six of nine features held one file per directory.

### A16. Delete the unused `FormElements.tsx`, or keep it? **[product deferred to us]**

**Chose:** keep, with a comment explaining why.

Nothing imports it, so Rollup excludes it entirely — bundle hashes are unchanged,
meaning it costs users **zero bytes**. Deleting would guarantee rewriting the same
primitives soon, since the profile/registration/accommodation forms all hand-roll
their inputs and are due for a rewrite against the real API. The comment also warns
against duplicating them inside a feature — the failure mode that produced the
duplicate `handleIdChange`.

### A17. Local Google OAuth configuration **[product]**

**Chose:** reuse the staff client ID locally; separate External client in production.

`config/participantAuth.js` falls back to `GOOGLE_CLIENT_ID` and `JWT_SECRET` in
development, and **throws in production** if `JWT_PARTICIPANT_SECRET` is missing, so
a misconfigured deploy fails loudly instead of silently signing participant tokens
with the staff secret.

Console note: browser-side Google Identity Services validates **Authorized
JavaScript origins**, not redirect URIs — `http://localhost:3001`, origin only, no
path.

### A18. Dev workflow **[product]**

**Chose:** `npm run dev` runs all three apps with named prefixes; `dev:staff` and
`dev:public` for pairs; `strictPort: true` so the event site never drifts off the
port whitelisted with Google.

### A19. Deliberate non-decisions

Things we chose **not** to do, and why:

- **`strict: true` in TypeScript.** Both frontends run `strict: false`. Turning it
  on across 13k lines is its own scoped task; mixing it into a structural move
  would have made the diff unreviewable.
- **Computing the payment amount.** `submitPaymentProof` inserts `amount = 0` with
  a TODO. A plausible-looking calculation would be worse than an obvious blank —
  it is the one number that must be right, and it depends on a profile method not
  yet written.
- **Retiring `server/modules/events/`.** It implements the legacy design and queries
  tables that no longer have a schema, so it is already non-functional in
  production. Its own PR.
- **Enabling rate limiting.** `express-rate-limit` is a dependency, commented out.
  Flagged, not switched on, because it affects every existing route.
